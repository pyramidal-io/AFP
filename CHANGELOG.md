# Changelog

All notable consumer-facing changes to this public AFP snapshot are recorded
here. This is the initial public baseline; it does not reconstruct private
development history.

Dates identify prepared draft baselines, not publication or production
qualification.

## [0.3.14-draft] - 2026-11-20

### Added

- AFP `0.3.14-draft` defines `afp:credential-envelope:v1` for native ZKC presentations and authenticated proof requests inside an encrypted AFP session. Credential-only exchanges require no ZKA transaction or coordination proof. The schema, signed-content vectors, replay checks and native Introduction Tier policy adapter are included; cryptographic subject/APR binding remains deployment-supplied, and synthetic test adapters do not establish production interoperability.
- The new non-normative `docs/afp_implementation_security_guide.md` describes how the Python reference meets §12.7.1, §12.7.2 and §15.5: mint tokens, closures, issued-instance sets, the HMAC-SHA-256 seal on `AcceptedPaymentQuote`, the `PaymentReceiptVerificationContext` composition root, the SQLite store modes, and the in-process trust boundary.

### Changed

- The Python reference's `verify_directory` now rejects an unusable verifier clock with `DirectoryError` before it evaluates the validity window. The supplied `now` and the default time source must each be a finite integer or float; NaN, infinities, booleans and non-numbers are rejected, where NaN used to pass both freshness comparisons. A finite clock behaves as before: `valid_from` is inclusive and `valid_until` is exclusive. No specification text, wire record or `interface_set_id` changes.
- §8.4 of the AFP Federation Mixnet now states the transport budget of `ob2-baseline-v1` as ideal model figures that can be recomputed: one leg of mixing (Erlang, shape 3, scale 30 s: mean 90 s, 95th percentile 188.9 s), two sequential legs (mean 180 s, 95th percentile 315.4 s), the slot wait, fragments that mix in parallel, and the per-tenant payload ceiling of 409.6 bytes per second at the minimum schedule. The rationale no longer calls all coordination latency-tolerant: it names `pay` as latency-sensitive, and a faster timing class for `pay` alone is a separate privacy design that owes its own §8.2 evidence. §15.5 adds a dispatch admission recommendation (`AFP-0505`): before an execution attempt and before broadcast, the payer checks deployment-measured estimates for dispatch, inclusion and route-evidence delivery against the quote and session deadlines, and does not proceed when they do not fit; it can then requote, decline or defer. `AFP-0506` recommends reconciling an uncertain earlier attempt before dispatching against a fresh quote. No minimum quote lifetime is set; the §15.6 inclusion bound, the §15.4 vector and the `ob2-baseline-v1` parameters are unchanged. No wire record, vector, fixture or `interface_set_id` changes (document revision 55; AFP Federation Mixnet document revision 4).
- §8.1 no longer says that no colluding minority of relays can learn a tenant pairing. It now states what the three-layer topology supports: a coalition of mix-node operators can directly trace every packet whose whole path it holds, a fixed fraction of packets (one in 27 for one node of three in each layer), so if that fraction is not zero, over sustained traffic it will almost certainly trace some packet of a pairing. That fraction is a lower bound: other inference and active attacks are not bounded, and §8.2 property 3 now requires correlation-resistance mechanisms and, with any OB-2 claim, the threat model, the traffic and deployment assumptions and the evidence for each correlation-resistance property claimed. A sender now chooses each packet's path uniformly among paths whose three nodes have three different `operator_aid` values (§8.4), so no coalition of one or two operator AIDs holds a whole path. §8.7 states that the directory cannot prove that different operator AIDs are independent parties, and §8.10 lists these limits. `AFP-0278` and `AFP-0281` are withdrawn and superseded by `AFP-0501` and `AFP-0502`; `AFP-0503` and `AFP-0504` are new. No wire record, vector, fixture or `interface_set_id` changes (document revision 52; AFP Federation Mixnet document revision 3).
- §12.7.1, §12.7.2 and §15.5 no longer state reference-implementation internals as requirements. Each section now states the outcome in language-neutral terms. A Coord v2 completion record must survive a restart. Any later use of an accepted credential must confirm the exact unchanged record and a live session. Dispatch authority comes from the instance's own session state, never from a stored token. The acceptance ledger, finality verifier and clock are fixed by deployment configuration. An accepted quote executes at most once, including across a restart. A deployment must not run untrusted extensions with acceptance and route authority. No wire record, vector, fixture or `interface_set_id` changes, and the reference behaviour is unchanged (document revision 45).
- The specification no longer narrates earlier releases in its normative sections. The rules those passages carried stay as present-tense requirements: a witness receipt signed over the bare event digest is rejected with no fallback (§4.4.2), and a session atom with a numeric `expires_at` is non-conforming and must be re-proposed, not translated (§12.2.1). The statement that AFP-KDC v1.0.3 uses the v1.0.2-named Poseidon2 parameter and conformance artifacts now appears once, in Appendix A. The three frozen v1 forms, `afp.telemetry.instance_attestation.v1`, `afp:zkc-presentation-context:v1` and `afp:credential-presentation:v1`, stay frozen until the next protocol-family interface epoch; their compatibility rules are stated once, in the new §12.9. No wire record, predicate, vector or `interface_set_id` changes (document revision 46).
- AFP-KDC (`docs/kdc_specification.md`, document revision 2) and the AFP Federation Mixnet (`docs/afp_routing_specification.md`, document revision 2) now give each normative statement a stable identifier, `[KDC-NNNN]` or `[AFP-NNNN]`, at the start of the statement. The new `docs/afp_requirement_index.json` (format `afp:requirement-index:v1`) lists each identifier with its section, keywords and scope, and `scripts/afp_requirement_ids.py check` validates it. The website page gives each identifier an anchor. The text of the statements and the wire surface are unchanged. The introduction profile (`docs/afp_introduction_profile.md`, document revision 3) follows the same scheme with `AFP-0023`–`AFP-0042`; the core specification (document revision 50) carries `AFP-0043`–`AFP-0499`, and §1.5 and §1.5.1 cite the identifier ranges. Each index entry records `text_sha256`, a digest of its statement text, so a statement and its entry cannot drift apart unnoticed. The index accepts an `applies_to_correction` record (the earlier label and a reason) so a reviewed correction of a conformance-subject label does not change the identifier.
- The specification no longer calls AFP identifiers "KERI AIDs" without qualification. An AFP AID has KERI semantics in the AFP encoding of §4.4.2, which is not KERI/CESR wire-compatible, and §10 now lists multi-key controller signing as an open item: a tenant root is one Ed25519 key, with no multisig. The encoding rules, vectors and typed records do not change (document revision 51).
- A note in §13.2 explains that the versioned AFP citations in the published `pay`, `pay_venue` and `afp.introduction` descriptors identify the retained publication of those profile definitions and do not track the current core interface version. The descriptors are unchanged. §3.5 no longer calls an OB-1-only deployment a "lesser tier"; it is an honest-disclosure interim that must be labeled as delivering OB-1 and not OB-2, and its obligation is unchanged (document revision 53).
- §14.7 of the introduction profile (`docs/afp_introduction_profile.md`, document revision 4) no longer promises a "portable negative-history record". The record had no format, signer rule or verification rule, it conflicted with the ban on portable reputation in §1.2, and showing it to a third tenant would reveal a pairing that OB-2 protects. Section 14.7 now says that financial recourse for a default is limited to the pre-posted escrow, that the §12.5 dispute and arbiter procedures and the downgrade and termination paths are unchanged, and that AFP defines no portable record of a default for use as reputation with future counterparties. The sentence in core §1.2 (document revision 54) that excused the record is removed. The ban on portable reputation is unchanged. No wire record, vector or interface surface changes. The `default` field of `Termination` in the Python reference keeps its shape; only its comment changed.
- New §1.6.1 lists the wire encoding of every time-valued member of every registered `afp:*` record: a whole-second UTC string, a Unix-seconds integer, or a JSON number, with its range and the rule that fixes it. `AfpCommitSignature.signed_at` is any finite binary64 value in RFC 8785 number form (AFP-0422), and its bytes do not change. The `afp:envelope:v1` times outside the §12.7.1 completion path and two `afp:provisional-agreement:v1` policy times stay unresolved. The Python reference now rejects a received `signed_at` that is missing or not an RFC 8785 number instead of substituting the local clock, and rejects a v2 attestation window or an introduction request window that starts before 1970 or is not ordered. It does not yet emit `afp:anchor:v1` `block_timestamp` or `afp:mixnet-directory:v1` `valid_from`/`valid_until` as UTC strings (document revision 56).
- The Python reference now emits and parses the `afp:provisional-agreement:v1` policy in its published §14.4 shape. Each `accepted_credentials` entry is a `{class, valid_until}` object (`AcceptedCredential`), not a JSON array, and `valid_until` and `agreement_expires_at` are strings, not JSON numbers. `bond_ref` and `last_commitment_ref` are absent when unset, never `null`. The emitter writes only an agreement signed by both parties and applies every check the reader applies, so whatever it emits reads back and re-emits unchanged; an unsigned draft is digested through `content()`. The reader rejects the array and number forms and does not translate them. It accepts any string for the two times and keeps it unchanged, because §1.6.1 still leaves their spelling unresolved; the reference fixtures use the §1.6.1 UTC datetime string. `content_digest` covers the wire object. An agreement made by an earlier release therefore has a different digest; parties that want to continue under it sign a new one. No specification text, wire record or `interface_set_id` changes.
- The Python reference now emits `afp:anchor:v1` `block_timestamp` and `afp:mixnet-directory:v1` `valid_from`/`valid_until` as §1.6.1 UTC datetime strings, and the directory's witness quorum signs that text. The constructors and the emitters reject a number or any other spelling, and the directory verifier rejects a window that is not two UTC strings. The directory builder rounds an explicit start up, a default start to the current whole second and the end down, and rejects an empty window or an unusable or overflowing scheduling input. `sign_payment_quote` accepts a caller's integer `signed_at` only when binary64 holds it exactly, so it never rounds the value; the reader's rule for a received token is unchanged. An anchor or directory made by an earlier release carries numbers and fails, and nothing is translated in place. An anchor record is rebuilt from its block and inclusion evidence, and its signed commitment is kept. A directory is rebuilt and re-signed by its witness quorum. No specification text, wire record or `interface_set_id` changes.
- §14.4 of the introduction profile (`docs/afp_introduction_profile.md`, document revision 5) now names the bytes that both `afp:provisional-agreement:v1` signatures sign. The agreement content is `kind`, `tier`, `policy` and `reputation_state` with their wire values, plus each signature object reduced to its `signed_by`; `kel_event_dig`, `signature` and `signed_at` are outside it, so both parties fix both signers before the first signature. The content hash is `D_` followed by the lowercase hexadecimal SHA-256 of the RFC 8785 JCS bytes, and each party signs the 66 ASCII octets of that hash, as for the §12.2.1 session content and the §15.3 quote content. Strings, including the two policy times, are hashed as carried, so no time spelling is fixed. Numbers are binary64 values in the RFC 8785 number form; an agreement that holds a number no binary64 value represents cannot be signed. Each signature verifies only in its own role, by that party's tenant root or delegated entity AID, at its current key state. The section also states how these signed bytes stay separate from every other payload an AFP key signs (AFP-0104). The new identifiers are `AFP-0508`–`AFP-0520`. The Python reference digests the agreement over these JCS bytes, signs and verifies both signatures (`afp_introduction.signing`), and pins vectors for a fixed agreement. `content_digest` of an agreement is now this content hash instead of a sorted-key `X_` digest, and an unsigned draft has one only when both signers are planned. This clarifies signature coverage that was not specified before, over unchanged fields: no wire record or field changes, `interface_version` stays `0.3.14-draft`, and `interface_set_id` does not change.
- The §12.2.2 session lifecycle diagram now matches the normative rules and the reference state machine. Expiry leads to `EXPIRED` from any non-terminal state. Rejection and either-party exit lead to `ABORTED`. Only `CLOSING` leads to `CLOSED`, and no transition leaves a terminal state. `OPEN` now means mutually authenticated and signed by both parties, with the §5.2 channel established from that signed session. This is editorial: behavior, wire records and the interface surface do not change (document revision 57).

## [0.3.12-draft] - 2026-10-28

### Changed

- Public CI's secret scanner now accepts the exact test call to the directory verifier with public witness keys and quorum `2`. The exception does not cover other paths, changed calls, or appended key material.
- OB-2's documented limits now state that federation membership remains visible and that mixing and cover traffic mitigate, but do not eliminate, long-horizon statistical disclosure, especially in small federations (§3.1, §8.10).
- Implementation and tenant conformance now share an explicit scope, with profile requirements applying when claimed and Appendix A applying when deriving keys with AFP-KDC. Tenant-to-operator telemetry requires authenticated endpoints and verified expected proof bindings, and fails closed when the existing proof context cannot be authenticated (§1.5, §1.5.1, §6.1, §12.1).
- Presentation conformance now reports a vector rejected during construction as `not_exercised`; that result does not count as verifier rejection or support a conforming verdict.
- Session proposal and envelope operations now reject profiles absent from the instance registry (§12.4). Namespace validation rejects empty, dotted, or wildcard tenant labels, and subject construction requires an explicit registration result. §12.4 clarifies that bilateral subjects use the sender’s tenant label. The existing subject tree and valid on-wire labels are unchanged.
- §4.4.2 now defines AFP's KEL encoding normatively: the event fields, RFC 8785 JSON, SHA-256 event digests and AIDs, `E_`/`D_`/`K_` qualified values, the next-key commitment, and domain-separated controller-signature and witness-receipt preimages, with known-answer vectors. KERI/CESR wire interoperability is a §10 open item. §6.3.1 key-state fields carry these event digests and the implicit single-key signing thresholds. Existing bare-digest reference witness receipts must be replaced by fresh prefixed signatures; verifiers provide no legacy fallback. Receipt attachments do not alter AIDs or event digests.
- A `pay` or `pay_venue` party that learns of a payment late can now claim it (§15.5, §15.6, §15.8, §15.9). The new observation claim needs no live session and no unexpired clock. It accepts a transaction only when the receipt matches the route, its finality meets the policy's `required_finality`, and the finality verifier proves inclusion strictly before `expires_at`. A rejected observation does not consume the route claim, and one transaction still settles at most one quote. Before, a party that first learned a `transaction_id` at or after `expires_at`, or after the session ended, could not claim it. Dispatch keeps its window. In the reference, this is `PaymentReceiptVerificationContext.route_from_observation`. The wire is unchanged.
- Only the payee's tracker can represent a `pay` v1 interaction as settled (§15.6, §15.8). The other principal's tracker reports dispatch and inclusion only. Before, §15.6 let that tracker settle once it held the payee's slot-0 disclosure, but v1 defines no record that carries it. One Aztec transaction also settles at most one `pay_venue` v2 quote (§15.9), as the shared ledger already enforced. The wire is unchanged.
- `pay` quote, signed-record and policy hashes are now pinned to RFC 8785 JCS bytes (§15.3, §15.1, §15.9). Before, the specification said only "sorted keys, compact separators", so encoders that escaped non-ASCII text or `<` produced other hashes. A new §15.3 vector pins a non-ASCII, escape-sensitive `quote_id`. Quote and policy bytes are unchanged. `acceptance_record_hash` now spells an integral `signed_at` without a fractional part, so it changes for such signatures. A v1 quote now requires an `X_` `session_context` at construction and decoding (§15.2), and `derive_interaction_context` accepts only a `D_` quote hash and an `X_` session context (§15.4). §15.4 no longer repeats its digest-mapping paragraph three times.
- `acceptance_record_hash` is local to each acceptor, and nothing published pins its old value. A `SQLiteReplayStore` created earlier keeps its rows and needs no migration. A quote accepted before this change and presented again after it gets a different record hash, so the store rejects it with "quote_id was already accepted with different content". The store already rejected such a duplicate, with a different message. No compatibility path is provided.
- A `pay` receipt tracker can no longer run under a weaker policy than the session's (§15.1, §15.5). `AcceptedPaymentQuote` now retains the live session's `profile_policy_hash` under its seal. Tracker creation rejects a policy with a different hash, and dispatch rejects a session with a different hash. Before, a tracker built with `required_finality: safe` reported settlement for a session opened under `finalized`. The v1 quote wire is unchanged.
- `pay_venue` v2 states the same dispatch window as `pay` v1 (§15.9). Dispatch requires the live `pay_venue` session, fails closed outside the quote window or after the session ends, and does not consume the route claim when it fails. `safe` or `finalized` evidence must prove inclusion before `expires_at`. The new `docs/payment_venue_v2_dispatch_conformance_v1.json` artifact pins the dispatch and inclusion cases.
- One transaction can no longer settle several `pay` quotes (§15.5, §15.6). APL must submit each AFP payment in its own Base transaction, although ZKA/Pay batches can carry up to `MAX_PAYMENTS`. Both reference ledgers refuse a `transaction_id` that another accepted quote has claimed; the SQLite ledger adds a unique index and fails closed at start-up if existing claims collide. `safe` or `finalized` evidence must now show, from the chain, the receipt's `interaction_context` and the configured `pool_context` in the payment's public inputs and one payment in the transaction, plus the payee's holder disclosure of the slot-0 note with the signed amount. Before, a verifier that met the v1 minimum could settle a quote with any pool transaction at the right finality. The v1 wire is unchanged.
- `pay` route dispatch is now bound to the quote window and the live session (§15.5). Dispatch requires the live-session capability on the call, and it fails closed when the deployment's trusted clock is at or after `expires_at` or before `quoted_at`, or after the session ends. A rejected dispatch does not consume the route claim. The finality verifier now receives the quote's `expires_at`, and `safe` or `finalized` evidence must show inclusion strictly before it (§15.6), so a late transaction leaves the obligation unsettled. Before, an accepted quote could be dispatched and settled at any later time, which gave the payer a free option on the signed WETH amount. In the reference, `PaymentReceiptVerificationContext` takes a required `clock`, `route_from_accepted` takes a required `live_session`, and `FinalityEvidenceVerifier.verify` takes `expires_at`.
- The specification no longer claims that entities sign with a key derived from their sub-seed `M'`; Appendix A defines no such derivation. Entities sign with their current KEL key, and §4.4 requires KEL keys, current and pre-rotated, to be independent of `M` and `M'`, so that compromise of the online seed does not defeat pre-rotation. Appliance migration (§4.7) carries the KEL keys explicitly.
- §4.6 no longer requires a guardian mechanism that neither KERI nor AFP defines. Loss of current keys is recovered by a pre-rotated rotation, and a delegated entity by tenant revocation and re-delegation. Tenant-root recovery after loss of the pre-rotated keys is a new §10 open item. No guardian or third-party event may change an AID's key state, and the tenant profile's recovery obligation matches.
- Responders now enforce session uniqueness (§12.2.1). A responder keeps a replay record of each proposal it signs, for at least the session's lifetime plus its clock skew. It rejects a proposal that reuses a recorded (initiator, `id`) pair or `session_context`, whether that session is live or terminal, as well as an expired proposal or one whose `opened_at` is beyond its clock skew. It checks all of this before changing any state. Each context therefore names exactly one responder-signed session. A colliding or replayed proposal can no longer evict, rewind, or relabel a live session, and an initiator can no longer reuse one context for a session under a different agreement or policy.
- The signed `afp:session:v1` stable content is now specified (§12.2.1): exactly nine members, RFC 8785/JCS canonicalization, a `D_` SHA-256 content hash, and an Ed25519 signature over that hash's ASCII bytes. `expires_at` and `closed_at` are whole-second UTC `YYYY-MM-DDTHH:MM:SSZ` strings, with `expires_at` strictly later than `opened_at`, and `closed_at` is omitted until set. A new conformance fixture pins a full preimage, content hash and signature, and the `afp:sealed:v1` channel KAT is regenerated over the corrected content hash.
- Verifiers must obtain current KEL state from the counterparty's witnesses or their own watchers, never from the counterparty alone. They must retain the latest KEL they have accepted per AID, rejecting a truncated KEL as `kel_keystate_stale` and a forked one as duplicity, except KERI superseding recovery (§4.5). Verifiers must query at least `n − t + 1` witnesses of the policy in force, and threshold-0 KELs get no witness protection. The reference's `keri.KelStateStore` does the retaining: each `Instance` keeps one and consults it during session establishment, envelope receipt, and payment-quote acceptance, and callers can pass one to the channel, commitment, and dispute verifiers.
- Durable records — commitments, divergence records, and arbiter decisions — can now be verified against the key state their `kel_event_dig` pins (§12.3), with `historical=True` in the reference. A routine rotation or a later revocation no longer voids them, so neither can be used to repudiate a signed record. Live acceptance still rejects a superseded key, and is still the default.
- Commitment, divergence-record, arbiter-decision, and payment-quote signers now pin `kel_event_dig` to the signer's latest establishment event, as the session core already did (§12.2.1, §12.6.1). A tenant root that has delegated an entity, or an entity whose KEL ends in an interaction event, can again produce signatures that verify.
- A tenant now approves every rotation of its entities and can revoke them, by anchoring seals in its own KEL (§4.2). An entity rotation the tenant has not anchored is rejected. An entity whose delegation the tenant has revoked is rejected permanently, by the session core and the §6.3.1 key-state resolver alike, which now share one delegation rule. `Identity.rotate` on an entity anchors the rotation in its tenant's KEL, and `Identity.revoke_delegation` revokes one.
- The sealed channel's replay window now slides forward on any authenticated frame ahead of it, as IPsec and DTLS windows do. Before, a frame more than 64 sequence numbers ahead was rejected, so losing 64 consecutive frames in transit permanently blocked that direction of the session. Duplicates and frames older than the window are still rejected.
- Session principals must be entity delegated AIDs (§12.3). A self-rooted (`icp`) AID is no longer accepted as an entity of whatever tenant it claims, and the claimed tenant's KEL must itself verify as a non-delegated root. Session acceptance, the sealed channel, commitments, dispute records, and payment-quote authentication all inherit the rule through `verify_kel`, which now treats a supplied tenant KEL as a demand for a `dip` delegated by that tenant.
- Every KEL event must now carry a controller signature from the key set that authorizes it (§4.4). Inceptions are signed by their own key, rotations by the pre-rotated key they reveal, and interactions by the current key. Interactions can no longer change keys, the next-key commitment, or the witness policy. The witness policy in force is the latest establishment event's, and every rotation must also be receipted under the policy it replaces (§4.5). Session, channel, commitment, dispute, and payment-quote verification inherit these rules through `verify_kel`.
- The §5.2 channel now has forward secrecy. Each endpoint draws a fresh X25519 scalar from a CSPRNG for every establishment, never transmits it, and erases it once the traffic keys are derived. The `M'` hierarchy only authenticates the ephemeral public key through the KEL-current signature. Before this change the scalar was derived from `M'` and a salt published in the attestation, so anyone holding one party's `M'` and a recording of the session could decrypt it. The channel KAT now pins its ephemeral scalars as explicit inputs; every derived value and frame byte is unchanged.
- An earlier publisher-last resync set the machine-checked composition boundary to family epoch `zka:protocol-family:2026-09-10.1`, pinning ZKM `0.1.0-draft (rev 12)`, its statement-set identity, and its Nargo 1.0.0-beta.25/Barretenberg 5.0.0 proving toolchain. AFP wire/profile surfaces, shared parameters, and deployment qualification were unchanged by that resync. The current composition coordinates are listed under Compatibility.
- AFP `0.3.12-draft` includes the separate experimental `pay_venue` v2.0 descriptor and policy, quote, and receipt v2 records introduced at family epoch `zka:protocol-family:2026-09-06.1`. V2 binds the exact venue, asset, recipient, amount, manifest, complete policy, and holder-disclosed receipt occurrence; the family pins AFP's interface-set identifier and conformance artifact. Publication does not qualify or activate a deployment, and the Base-only `pay` v1.0 bytes, hashes, vectors, and route semantics remain unchanged.
- The presentation-context v2 change introduced in AFP `0.3.11-draft` binds the verifier-selected trust flow into the current `afp:zkc-presentation-context:v2` transcript as one of four namespaced purposes, maps the SHA-256/JCS digest canonically into a nonzero BN254 scalar, and requires the ZKC result to return a proof-authenticated credential-subject AID. Verification rejects legacy v1, missing-purpose, cross-flow, noncanonical/zero-field, and subject-mismatch cases; it still independently compares the ZKC-verified atomic predicates against the caller-authenticated policy for that flow.
- Every Ed25519 signature consumer now uses one strict verification boundary that rejects malformed lengths, non-canonical or non-prime-order points, identity and torsion encodings, mixed-order points, and non-canonical scalars. Production verifier adapters must pass the published executable conformance cases before use.
- An earlier composition update targeted ZKA `0.9.2-draft` at epoch `zka:protocol-family:2026-09-04.1`. AFP atoms, envelopes, and presentation preimages retain their canonical `X_` session digest; ZKA bundle, transaction, binding, and Coord field contexts use its exact nonzero big-endian BN254 projection, while contained ZKC verification uses AFP's distinct authenticated v2 presentation context. The published §5.2 vector pins both session representations. `zka:bundle:v1` shape, ZKC proof ABIs, AFP-KDC parameters, and ZKM statements are unchanged. The current composition coordinates are listed under Compatibility.
- The privacy boundary now states that a terminal mixnet relay necessarily receives an opaque per-session destination value while receiving neither tenant AID nor the relationship mapping, and that resistance to offline candidate testing requires bilateral secret material rather than the bundled clean-room helper's unkeyed derivation.
- Session proposals now carry an authenticated responder binding whose entity AID is committed by the initiator-signed session context before recipient recomputation. Acceptance preserves that binding and adds only the responder signature, rejecting proposals replayed to a different responder.
- The signed `opened_at` wire value is now pinned to an RFC 8785/JCS JSON integer number from `0` through `253402300799`, in canonical unsigned decimal, with published cross-runtime conformance vectors.
- Private-reconciliation and reciprocal-exchange workflows now compose the existing AFP session context and accepted workflow policy with canonical ZKA Coord v2 final receipts. Completion pins immutable profile/artifact coordinates and requires a deployment-bound verifier to authenticate the fresh complete bundle, final proof, and opaque evidence references before one atomic durable replay/effect record; direction, retry, retransmission, redaction, and generic-ingress failures are fail-closed.

### Compatibility

- The successor publisher-last resync consumes family epoch `zka:protocol-family:2026-10-26.1` and ZKM `0.1.0-draft (rev 13)`, with its coordinated positive-spend rule and policy diagnostics. The canonical inventory now documents the six-field CredNote storage transcript. Existing ZKC historical and successor toolchain lanes remain distinct. AFP stays `0.3.12-draft` with the same interface identity, ZKA/ZKC/AFP-KDC versions, wire/profile records, KDC values, and deployment/route gates.
- Witness receipts now sign `afp:kel-receipt:v1`, a zero octet, and the event digest, rather than the bare digest. Receipts made under the earlier preimage no longer verify; witnesses must re-receipt existing events.
- The Python reference `Instance` refuses to propose or accept a session `id` it already holds, and gains a `max_clock_skew_seconds` parameter (default 300). Callers that reused a session id for a new session must choose a fresh one. This is a document-revision change: the AFP interface version, interface digest and protocol-family epoch are unchanged.
- Earlier Python-reference releases signed `expires_at` as a JSON number (for example `1700003600.0`) under non-JCS canonical JSON, so their session content hashes, signatures and channel transcripts do not reproduce under RFC 8785. Those atoms are now rejected; re-propose the session rather than translating it. `closed_at: null` is likewise rejected. This is a document-revision change: the `afp:session:v1` record text, the AFP interface version, interface digest and protocol-family epoch are unchanged.
- Entity KELs whose rotations were never anchored by their tenant are rejected. Have the tenant anchor each such rotation, or re-delegate the entity.
- A caller that passed a tenant KEL alongside a tenant-root (`icp`) signer's KEL must now omit `tenant_kel` for that signer. Conforming sessions are unaffected, because their principals are already delegated entities.

A commitment signature, divergence record, or arbiter decision whose named signer AID differs from the verified KEL is rejected.
- KELs produced by earlier Python-reference releases carry no controller signatures and are rejected. So are KELs with interaction events that change establishment state, and witness changes receipted only by the new witness set.
